# หลังบ้าน — PocketBase

ไบนารี Go ตัวเดียวที่ให้ REST API, auth, realtime, กฎสิทธิ์ และหน้า admin
เลือกใช้เพราะประหยัดเวลาพัฒนาไป 30–40 คน-วัน เทียบกับเขียน backend เอง
(เอกสารออกแบบหัวข้อ 04)

## เริ่มใช้งานในเครื่อง

```bash
npm run pb:up                      # เปิด PocketBase ที่ :8095
docker exec prakaipos-pb pocketbase admin create dev@prakaipos.local devpassword123 --dir /pb_data
node backend/seed.mjs              # ใส่ข้อมูลตัวอย่าง 2 ร้าน

# ตรวจกฎ/hook สิทธิ์ทั้งหมด — พังแล้วเงียบไม่มี error ให้เห็น ต้องรันหลังแก้
# อะไรก็ตามที่เกี่ยวกับ createRule/updateRule/pb_hooks
node backend/verify-isolation.mjs         # แยกข้อมูลระหว่างร้าน
node backend/verify-auth.mjs              # เข้าระบบด้วย PIN
node backend/verify-qr-order.mjs          # เส้นทาง QR Order
node backend/verify-menu-price-guard.mjs  # พนักงานแก้เมนูได้แค่ sold_out
node backend/verify-plan-guard.mjs        # แผนสมาชิก/บล็อก QR Order ตอน trial
node backend/verify-stock-deduct.mjs      # ตัดสต๊อก/คืนสต๊อกอัตโนมัติ
```

หน้า admin: <http://127.0.0.1:8095/_/>

## โครงสร้างข้อมูล

| Collection       | หน้าที่                                              |
| ---------------- | ---------------------------------------------------- |
| `shops`          | ร้าน — รหัสร้าน, เลขพร้อมเพย์, โหมด QR Order          |
| `staff`          | พนักงาน (auth collection) — ล็อกอินด้วย username + PIN |
| `categories`     | หมวดเมนู                                             |
| `menu_items`     | เมนู — ราคาเป็นสตางค์                                |
| `table_sessions` | รอบนั่งของโต๊ะ สำหรับ QR Order                       |
| `orders`         | บิล — รายการอาหารฝังเป็น JSON ในตัวบิล                |
| `devices`        | เครื่องที่ลงทะเบียน + ช่วงเลขบิลที่จองไว้              |
| `ingredients`    | วัตถุดิบ — หน่วยนับอิสระ, ต้นทุนต่อหน่วยเป็นสตางค์, คงเหลือปัจจุบัน |
| `stock_movements`| เลดเจอร์การเปลี่ยนสต๊อก (รับเข้า/ตัดออก/นับสต๊อก) — แก้/ลบไม่ได้ |

`menu_items.recipe` และ `menu_items.modifier_groups` เป็น JSON ฝังในตัวเมนู
(สูตรอาหาร/BOM และตัวเลือก-ท็อปปิ้งตามลำดับ) ด้วยเหตุผลเดียวกับที่ `orders.lines`
ฝัง JSON — แก้พร้อมกับเมนูเสมอ ไม่มีใครอ่านแยก

### ต้นทุน/กำไร (ก้อนที่ 2)

`recipeCost()` (ฝั่งแอป `menu/cost.ts`) คิดต้นทุนจากสูตร × ราคาวัตถุดิบ **ปัจจุบัน**
เสมอ ไม่ได้ snapshot ต้นทุน ณ เวลาขายไว้ในบิลเหมือนราคาขาย — ตัวเลขต้นทุน/กำไร
ในแดชบอร์ดและหน้าจัดการเมนูจึงเป็นค่าประมาณที่คลาดเคลื่อนได้ถ้าราคาวัตถุดิบ
เปลี่ยนหลังขาย เป็นการยอมแลกความง่ายตามหลัก "ทำเล็กก่อน" ของทั้งโครงการ

**สต๊อกยังไม่ตัดอัตโนมัติตอนขาย** — ตอนนี้ "ตัดออก" ต้องกดบันทึกเองที่หน้า
วัตถุดิบและสต๊อก การตัดสต๊อกอัตโนมัติตอนบิลปิด (ผูกกับ `orders` ที่ `channel=pos`
และ `status=paid`) ต้องพึ่ง record hook ฝั่ง PocketBase ที่ยังไม่ได้ทดสอบกับ
เซิร์ฟเวอร์จริงในโปรเจกต์นี้ — ตั้งใจเว้นไว้ก่อนเพื่อไม่ให้ส่งโค้ดที่ไม่มั่นใจว่า
ทำงานถูกต้อง รอทำก้อนถัดไปหลังทดสอบกับเซิร์ฟเวอร์จริงแล้ว

### ทำไมรายการอาหารถึงฝังใน `orders` ไม่แยกตาราง

แท็บเล็ตส่งบิลขึ้นมาทั้งใบเป็นก้อนเดียว ถ้าแยกตารางต้องทำ transaction
ข้ามตารางให้ถูกตอนเน็ตหลุดกลางทาง ซึ่งเป็นจุดที่พังง่ายที่สุดของระบบออฟไลน์
การฝังไว้ทำให้ "ส่งซ้ำแล้วไม่เกิดบิลซ้ำ" เหลือเป็นเรื่องของแถวเดียวล้วนๆ

แลกกับการที่รายงานเมนูขายดีต้องรวมยอดฝั่งแอป — ที่ 100–300 บิล/วันของร้านเล็ก
ไม่หนักพอให้เป็นปัญหา

### กันบิลซ้ำ

`orders.client_uuid` มี unique index แท็บเล็ตสร้าง UUID เอง ส่งซ้ำกี่ครั้ง
ก็ติด constraint ไม่เกิดแถวใหม่ — ทดสอบไว้แล้วใน `verify-isolation.mjs`

## QR Order — เสร็จแล้ว

ลูกค้าสั่งอาหารผ่าน `pb_hooks/qr_order.pb.js` สองเส้นทาง:

- `GET /api/public/table-session/:shopCode/:tableNo?k=ลายเซ็น` — ยืนยันลายเซ็น
  HMAC ของลิงก์โต๊ะ แล้วคืน (หรือเปิด) รอบนั่งปัจจุบันของโต๊ะนั้น
- `POST /api/public/orders` — สร้างออร์เดอร์จริง คำนวณราคาจากฐานข้อมูล
  ไม่เชื่อ `unitPrice`/`nameSnapshot` ที่ไคลเอนต์ส่งมาเลย

`orders.createRule` ถูกปิดไม่ให้สร้างผ่าน REST ตรงๆ แบบไม่ล็อกอินแล้ว
(ต้องล็อกอินเท่านั้น) ทุกออร์เดอร์จาก QR ต้องผ่านสองเส้นทางข้างบน
ซึ่งเขียนข้อมูลด้วย `dao.saveRecord()` ระดับแอดมิน ไม่ผ่าน createRule นี้

ทดสอบครบใน `node backend/verify-qr-order.mjs` — ลายเซ็นผิด/ไม่มี/ข้ามโต๊ะ,
โกงราคา, ของหมด, เมนูข้ามร้าน, รอบนั่งปิดแล้ว, จำกัดอัตรา, โหมด auto

**เลขบิลของ QR order เป็นค่าติดลบ** (`shops.next_qr_order_no` เดินหน้าลง)
แยกพื้นที่ตัวเลขจากเลขบิลของ POS ที่เดินหน้าขึ้นจากช่วงที่แต่ละเครื่องจองไว้
เหตุผลเต็มอยู่ในคอมเมนต์ของ `pb_hooks/qr_order.pb.js` — สรุปสั้นๆ คือ POS
ต้องรู้ช่วงเลขล่วงหน้าเพื่อทำงานออฟไลน์ได้ ส่วน QR order ออนไลน์เสมอจึงขอ
เลขจากเซิร์ฟเวอร์ได้ทุกครั้งโดยไม่ชนกัน **นี่คือเลขออร์เดอร์ชั่วคราว** ไม่ใช่
เลขใบเสร็จจริง — ก้อนถัดไปต้องผูกเลขใบเสร็จจริงตอนพนักงานปิดบิลที่เคาน์เตอร์

### ข้อจำกัดของ PocketBase JSVM ที่เจอระหว่างทาง

ฟังก์ชันและค่าคงที่ที่ประกาศไว้ **ระดับบนสุดของไฟล์ .pb.js มองไม่เห็นจาก
ภายใน callback ของ `routerAdd` หรือ `onRecordBeforeUpdateRequest`/hook อื่นๆ
ทุกชนิด** แม้ประกาศไว้ก่อนหน้าในไฟล์เดียวกัน — ทดสอบยืนยันแล้วทั้งสองแบบ
(เรียกแล้วได้ ReferenceError "is not defined" ทันที ล่าสุดพบใน
`menu_item_price_guard.pb.js`) ทุกอย่างที่ callback ต้องใช้จึงต้องประกาศ
"อยู่ภายใน callback เดียวกัน" เท่านั้น ดูรายละเอียดในคอมเมนต์หัวไฟล์ `qr_order.pb.js`

และการเทียบฟิลด์ `created` ในตัวกรอง (filter) ต้องใช้รูปแบบเวลาแบบเว้นวรรค
`"YYYY-MM-DD HH:MM:SS.sssZ"` ไม่ใช่ ISO 8601 แบบมี `T` คั่น — ใช้ `T` แล้ว
filter จะคืน 0 แถวเสมอโดยไม่มี error ให้เห็น (พบตอนทดสอบโค้ดจำกัดอัตราการสั่ง
ที่ไม่เคยทำงานเลยเงียบๆ)

และ `record.get()` บนฟิลด์ type `json` ที่**ไม่เคยถูกตั้งค่าเลย** คืนค่าดิบที่
ยัง truthy อยู่ (ไม่ใช่ `null`/`undefined`) แต่ `String(...)` แล้วได้ `""`
เปล่าๆ — เขียน `raw ? JSON.parse(String(raw)) : []` แบบเดิมจึงพัง (เจอ
`SyntaxError: Unexpected end of JSON input`) ทุกครั้งที่เมนูยังไม่เคยตั้ง
`modifier_groups`/`recipe` เลย ต้องเช็คความยาวของสตริงหลัง `String()` ก่อน
`JSON.parse()` เสมอ (แก้แล้วใน `qr_order.pb.js` และ `stock_deduct.pb.js` —
พบตอนรัน `verify-qr-order.mjs`/`verify-stock-deduct.mjs` ครั้งแรกหลังเพิ่ม
ฟิลด์ `recipe` ซึ่งเมนูส่วนใหญ่ในระบบยังไม่มีค่า)

## ยังทำไม่เสร็จ — ต้องทำก่อนเปิดให้ร้านจริงใช้

> **เลขบิลชั่วคราวของ QR order ยังไม่ถูกผูกเข้ากับเลขใบเสร็จจริง**
>
> ตอนนี้ order ที่มาจาก QR ค้างเป็นเลขติดลบตลอดไป ต้องออกแบบขั้นตอนตอน
> พนักงานปิดบิลที่เคาน์เตอร์ (หรือระบบแปลงอัตโนมัติในโหมด auto) ให้ผูก
> เลขบิลจริงจากช่วงที่เครื่อง POS จองไว้เข้ากับ order นี้

## สำรองข้อมูล

ข้อมูลทั้งหมดอยู่ใน `backend/pb_data/` (SQLite + รูปเมนู) — สำรองคือคัดลอกโฟลเดอร์นี้

บนเครื่องจริงต้องตั้ง cron คัดลอกขึ้น object storage รายวัน และ
**ทดสอบกู้คืนจริงทุกไตรมาส** ไม่ใช่แค่ตั้งค่าสำรองแล้วปล่อย (เอกสารออกแบบหัวข้อ 12)
