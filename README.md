# PrakaiPOS

ระบบขายหน้าร้าน (POS) สำหรับร้านอาหารเล็กใน จ.เลย — เปิดจากเบราว์เซอร์
ไม่ต้องลงแอป ทำงานตอนเน็ตหลุดได้ และมีระบบสั่งอาหารผ่าน QR Code รวมในราคาหลัก

เอกสารออกแบบฉบับเต็ม: [`docs/prakaipos-design.html`](docs/prakaipos-design.html)

## สถานะปัจจุบัน

**ขายได้จริงแล้ว ครบก้อนที่ 1 และ 2 ตามแผน** — เปิดบิล คิดเงินสด/พร้อมเพย์
พิมพ์สลิป จัดโต๊ะ ตัวเลือกเมนู แยกบิล คิดต้นทุนสูตรอาหาร ตัดสต๊อกอัตโนมัติ

PLAN.md เป็นหลัก)

## โครงสร้าง

```
apps/pos/        PWA หน้าขาย — React + Dexie + Service Worker
apps/order/      เว็บลูกค้าสแกน QR — เบา ไม่มี Service Worker
apps/admin/      แอปออก/ต่อแผนการใช้งานให้ร้าน (ทีมงาน ไม่ใช่ของร้าน)
packages/shared/ types, PromptPay, การคำนวณเงิน, การออกเลขบิล
backend/         PocketBase — schema, hooks, seed, สคริปต์ตรวจสอบ
docs/            เอกสารออกแบบ + แผนงาน (PLAN.md)
```

### ทำไมแยกเป็นสองแอป

หน้าลูกค้าต้องเปิดเร็วบนสัญญาณอ่อน ถ้ารวมบันเดิลเดียวกับ POS
ลูกค้าจะต้องโหลดโค้ด Dexie ระบบซิงก์ และหน้าจัดการเมนูทั้งหมดโดยไม่ได้ใช้เลย

## เริ่มพัฒนา

```bash
npm install

npm run pb:up                      # PocketBase ที่ :8095
docker exec prakaipos-pb pocketbase admin create dev@prakaipos.local devpassword123 --dir /pb_data
node backend/seed.mjs              # ข้อมูลตัวอย่าง 2 ร้าน
node backend/verify-isolation.mjs  # ตรวจกฎแยกข้อมูล
node backend/verify-auth.mjs       # ตรวจเส้นทางเข้าระบบ

npm run dev:pos                    # หน้าขาย  http://localhost:5183
npm run dev:order                  # หน้าลูกค้า http://localhost:5184/t/krua-nong/5
```

```bash
npm test         # เทสต์ทั้งหมด
npm run typecheck
npm run build
```

### ทดสอบพฤติกรรมออฟไลน์

**โหมด dev ไม่ลง Service Worker โดยตั้งใจ** เพราะ SW ในโหมด dev จะค้างอยู่
ในเบราว์เซอร์หลังปิด dev server แล้วดักหน้า `localhost:5183` ไว้
เสิร์ฟ shell เก่าที่ไปขอ `/src/main.tsx` จากเซิร์ฟเวอร์ที่ไม่มีแล้ว
ได้ `ERR_CONNECTION_REFUSED` เป็นพรืดจนดูเหมือนแอปพัง

และชุดไฟล์ที่ SW โหมด dev แคชไว้ก็ไม่เหมือนของจริง ผลการทดสอบจึงเชื่อไม่ได้อยู่ดี

ทดสอบออฟไลน์กับของจริงแบบนี้แทน:

```bash
npm run build -w @prakaipos/pos
npm run preview -w @prakaipos/pos     # เสิร์ฟไฟล์ที่ build แล้วพร้อม SW จริง
npm run pb:down                       # ปิดเซิร์ฟเวอร์เพื่อจำลองเน็ตร้านล่ม
```

ถ้าเครื่องเคยลง SW จากโหมด dev รุ่นก่อนไว้ แอปจะถอนให้เองตอนเปิดครั้งถัดไป
แล้วขึ้นข้อความใน console ให้รีโหลดหนึ่งครั้ง

## หลักการตัดสินใจ

คนทำคนเดียว เวลาคือทรัพยากรที่หายากที่สุด ทุกครั้งที่เลือกได้ ให้เลือกทางที่
**เขียนโค้ดน้อยกว่า ดูแลง่ายกว่า และซัพพอร์ตลูกค้าน้อยกว่า** แม้จะดูมีฟีเจอร์
น้อยกว่าคู่แข่ง เพราะระบบที่ล่มบ่อยทำลายธุรกิจเร็วกว่าระบบที่ฟีเจอร์น้อย

สิ่งที่ยึดในโค้ด:

- **เงินเป็นจำนวนเต็มหน่วยสตางค์เสมอ** ไม่มีทศนิยมในการคำนวณเงิน
- **เขียนลงเครื่องก่อนเสมอ แล้วค่อยส่งขึ้นคลาวด์** หน้าจอต้องตอบสนองเร็วไม่ว่าเน็ตจะเป็นอย่างไร
- **ทุกบิลมี UUID จากเครื่อง** ส่งซ้ำกี่ครั้งก็ไม่เกิดบิลซ้ำ
- **ข้อมูลการขายห้ามหาย** งานที่ส่งไม่สำเร็จค้างในคิว ไม่ถูกทิ้ง แม้จะทำให้คิวตัน
- **ไม่พูดเกินกว่าที่รู้** เช่น ตอนคิวว่างเราไม่ได้ติดต่อเซิร์ฟเวอร์เลย
  หน้าจอจึงบอกแค่ "ไม่มีรายการค้างส่ง" ไม่ใช่ "ข้อมูลตรงกับคลาวด์แล้ว"
- **ห้ามใช้ alert/confirm** กล่องของเบราว์เซอร์บล็อกทั้งจอ ถ้าโผล่กลางบิล
  พนักงานจะกดอะไรไม่ได้เลย

## ข้อจำกัดที่ต้องบอกลูกค้าตรงๆ

| อุปกรณ์               | ขายของ / QR Order | พิมพ์สลิป              |
| --------------------- | ----------------- | ---------------------- |
| แท็บเล็ต Android + Chrome | ได้               | ได้ (Web Bluetooth)    |
| iPad + Safari         | ได้               | **ไม่ได้**             |

Safari บน iOS ไม่รองรับ Web Bluetooth และ Apple ไม่มีแผนจะรองรับ
ร้านที่ต้องพิมพ์สลิปให้ใช้แท็บเล็ต Android

## เรื่องที่ต้องทำก่อนเปิดให้ร้านจริงใช้

ดูรายละเอียดใน [`backend/README.md`](backend/README.md)

- ตรวจลายเซ็น HMAC ของลิงก์โต๊ะ ก่อนรับออร์เดอร์จาก QR
- คำนวณยอดเงินฝั่งเซิร์ฟเวอร์ — ห้ามเชื่อยอดที่ไคลเอนต์ส่งมา
- จำกัดให้พนักงานแก้เมนูได้เฉพาะฟิลด์ "ของหมด"
- ตั้งสำรองข้อมูลรายวันออกนอกเครื่อง และทดสอบกู้คืนจริง
